## How we work
- **Read `knowledge/memory.md` first.** It is the canonical project-state snapshot - clients, motions, decisions, key people, tools. Everything else in `knowledge/` is depth on a specific topic.
- **Cross-model discovery:** this file is the canonical shared operating contract, and Claude Code's direct entrypoint. `ai/AGENT_ROUTES.json` owns workflow aliases and mode-scoped action ids, and `scripts/sync-agent-adapters` owns their fixed instruction text plus a compatibility floor that pins the mode set, the action ids and the minimum alias set: adding an alias is a registry-only edit, while removing or renaming one is a deliberate registry-plus-generator change. `AGENTS.md`, `GEMINI.md`, `.github/copilot-instructions.md`, every `.agents/skills/<name>/SKILL.md` and `.claude/skills/<name>/SKILL.md` adapter, and the thin Claude `/standup`, `/eod` and `/weekly` commands are generated views. Never edit those views by hand. Change the registry for routing, the canonical skill for procedure, or the generator's action map for a deliberate behavior change, then run `scripts/sync-agent-adapters --write`. `scripts/repo-doctor` blocks a stale or missing view and behaviorally challenges the generator before accepting its clean claim; its two agent-adapter check ids take file-scoped allow entries only, never `::token` scoped, and each HARD line names its exact entry. Both Claude Code and Codex own a built-in `/plan`, so that slash command stays reserved on each and natural planning phrases route through the generated daily-log skill. **Discovery is separate from ownership:** a skill is owned by its `skills/<name>/SKILL.md`; hosts that auto-discover skills read `.agents/skills/` (Codex, invoked as `$<name>` or through `/skills`) and `.claude/skills/` (Claude Code), so the registry carries one `skill_adapters` row per skill and the generator writes a thin adapter that points back at the canonical file. Adding a skill means adding that row and running the generator; the adapter is never the skill and is never hand-edited. The generator refuses to render an adapter whose canonical `SKILL.md` lacks `name` and `description` frontmatter, because that is the metadata a skills host keys discovery on, and `--check` fails when a `skills/<name>/SKILL.md` exists with no registry row.
- **Host layers (`.claude/`, `.codex/`):** the two are hand-maintained configuration, not generated views. `.claude/settings.json` and `.codex/hooks.json` wire the SAME guard scripts under `.claude/hooks/` (`deny-env-access.py`, `deny-destructive-git.py`), so each guard keeps one owner and only the wiring can drift; `.claude/agents/*.md` and `.codex/agents/*.toml` are two views of the same subagent and change together. `repo-doctor`'s `codex-parity` check is the floor: HARD when a guard is wired on one host and not the other, when a hook points at a script that is not tracked, or when a Claude agent has no Codex mirror; it takes file-scoped allow entries and each HARD line names its own. `scripts/test-git-guard` is the fixture suite that proves both guards still fire and that the Claude-side wiring is intact; run it after touching either hook or `.claude/settings.json`. Codex gates its layer twice, and the two gates are independent: project trust makes `.codex/config.toml` and the agents live, while hook trust is separate, per content hash, granted interactively, and NOT armed by cloning. Until you run `codex` at the repo root and accept the hook-review prompt, Codex runs this repo under the sandbox in `config.toml` with neither guard and says nothing about it; re-arm after ANY edit to `.codex/hooks.json`, because trust is a hash of the file. `repo-doctor`'s soft `codex-hooks-untrusted` line says so on a machine where Codex has run and this repo's hooks are untrusted. `.claude/settings.json` sets `worktree.bgIsolation` to `"none"`, so background agents run in the live tree; the "Agents and the live tree" bullet below is the containment. Both guards are command-string matchers and therefore a floor, not a fence: they deny the literal token and glob-shaped dotfile spellings, never a spelling that writes neither. Codex's own per-path filesystem deny (`"**/*.env" = "deny"` under a `[permissions.<profile>.filesystem]` profile) is the complete control there and is the operator's call to adopt; see `.codex/README.md`.
- Then read the topic-specific `knowledge/` files that match the task.
- **Then `ai/DECISIONS.md`, before any decision-shaped move** (pricing, scope, a gate, a commitment, a client send). Settled rulings are not re-argued. Pull `ai/ERRORS.md` and `ai/TOMBSTONES.md` on the same read whenever the task touches money, a client-facing artifact, or a number that has been superseded.
- `knowledge/` is authoritative. Write deliverables to `outputs/`.
- **Precedence on any conflict:** this file -> `knowledge/memory.md` -> topic files -> everything else. Two exceptions. (a) An explicitly dated update beats an undated claim from a higher tier. (b) A ruling recorded in `ai/DECISIONS.md` beats any restatement of it elsewhere, because that row owns both the ruling and its review date. Whenever either fires, fix the higher tier in the same session so the exception stays short-lived.
- **Writing `knowledge/`:** curated knowledge is updated as facts change, without asking first. Two limits hold. A write records something Sam actually said or a source file actually shows, never an inference dressed as state. And a canonical rewrite of `knowledge/memory.md`, or any reorganization of `knowledge/`, is Tier-2 work: run the hard-task protocol first (see Hard tasks below).
- `raw/` is quarantined. Ask before treating it as truth. Only mine it when explicitly asked to distill into `knowledge/`.
- **External reference vs adopted doctrine.** Third-party material (a course, a mentor's framework, a book's method) is reference by default: use it as input, never as the business's own voice, and never let it outrank a curated file. Formally *adopting* an external framework is a deliberate, recorded decision. An adopted framework lives in `knowledge/doctrine/<name>/` behind a `CORE.md` router, is read before any decision in the domain it governs, and its `CORE.md` must state plainly what it does **not** govern so nobody stretches it there. Adopted doctrine is doctrine, not state: normal precedence still holds, so a live client file beats a doctrine page on what is actually true today. See `knowledge/doctrine/README.md` for the slot and the adoption checklist.
- **Sensitive data:** bank and wire numbers live ONLY in the gitignored `knowledge/business/invoices/PAYMENT-DETAILS.md`. Never inline them in any committed file. The committed `PAYMENT-DETAILS.template.md` holds the placeholder scaffold; the real-values file is a local copy that is never committed. `personal/`, `outputs/ops/` and `outputs/invoices/` are local-only by design (gitignored; your cloud drive is the archive for issued invoices). Committed files may cite these local-only paths. Such pointers are intentionally dangling on a fresh clone. Citing is the limit: a committed file may **cite** a local-only path, never **restate** its contents. Name the fact class, not the counterparty, the ID, or the number. Provider API keys for the agent-hands scripts live ONLY in the gitignored repo-root `.env.local`: no AI tool may read or edit `.env*` in this repo, enforced mechanically by the deny rules and PreToolUse guard in `.claude/settings.json` plus `.claude/hooks/deny-env-access.py`. The wrapper scripts load the keys inside their own process; agents call the scripts, never the file. `.env.example` documents which keys exist without holding any.
- **Commit protocol:** a session that wrote `knowledge/` ends with commit + push. Git is the backup and audit trail for the repo that IS the business. A subagent's `knowledge/` write is committed by the parent session that spawned it. The pre-commit hook runs `scripts/repo-doctor --staged` on the staged set (blocks wire/account/phone/provider-credential shapes, protected paths, fake office files). The pre-push hook is the backstop a bypassed commit cannot outlive: it reads git's ref-update stdin, resolves what the remote actually holds with `git ls-remote` rather than from local tracking refs, and runs the full scan on every transferred commit in a throwaway worktree outside the repo, blocking and naming the offending sha. Resolving from local tracking refs is the trap: they can silently exclude the entire range and wave through hundreds of unscanned commits. Each commit is judged by THIS checkout's doctor and allow file, not the ones it carries, so a commit made while the doctor was weak cannot self-approve; `ai/TOMBSTONES.md` is the one input deliberately read from the scanned commit, because a commit made before a value was retired was legitimately clean. A range over its 50-commit cap blocks loudly rather than scanning a subset, and every exit path prints a line, because a push that could not be fully scanned is not a push found clean and a scan of nothing is never silent. One-time setup on a new clone: `git config core.hooksPath .githooks`, plus the weekly-backup launchd agent per the INSTALL block at the top of `scripts/weekly-backup`.
  - `git commit --no-verify` skips the staged check for that one commit, and staged mode never looks at that file again unless something re-stages it, so the push-time range scan is what catches it.
  - **The allow entry is read from the pushing checkout, not from the commit it excuses.** A scoped entry added in a LATER commit therefore does clear an older commit in the same range. That is the remedy when a tightened check retroactively condemns a defect an unpushed commit carried legitimately. The intuitive rule, that an entry must sit in the same commit as the content it excuses, is wrong, and believing it leaves no way out of a retroactive block. Keep such an entry occurrence-scoped (`<check-id> <path>::<token-glob>`), short-dated and reason-bearing, and delete it once the range lands.
  - `git push --no-verify` stays the strictly worse tool: it excuses nothing and skips the scan of every commit in the range.
  - Agent tool calls cannot run the bypasses or the destructive class at all: the PreToolUse guard `.claude/hooks/deny-destructive-git.py` (fixtures: `scripts/test-git-guard`) denies no-verify commits and pushes, sweep staging (`add -A`, bare-dot adds, `commit -a`), hard resets, forced cleans, worktree-discarding checkout, restore and switch forms, branch force-deletes and forced or deleting pushes; plain push stays open because this protocol requires it. Those commands are operator-at-the-keyboard tools, in a real terminal.
- **Agents and the live tree:** an agent never writes into this repo unless the task IS a repo write, and never relies on an inherited working directory to decide where it is. Use `git -C <abs>`, explicit `cwd=` on subprocesses, absolute paths in shell, and explicit-path staging, never `git add -A`. Probes and fixtures go in a throwaway clone outside the repo. Two failure modes make this non-negotiable: an agent that assumed its working directory committed straight to the main branch, and an agent running a "safe" regeneration against an inherited path destroyed a live tracker file by rebuilding it from a stale source. Background agents run in the live tree, so this bullet is the containment, not worktree isolation.
- Harness auto-memory is a hint, not truth: on conflict `knowledge/` wins; when saving a business fact to auto-memory, cite its canonical file. An auto-memory entry that is a CONTROL (something `ai/ERRORS.md` would name in a "Control that now prevents it" cell) needs a git-resident owner under `knowledge/`, with the auto-memory copy as the mirror: auto-memory sits outside git and outside `repo-doctor`'s scan, so a control kept only there has no history, cannot be diffed, and is not a path the error ledger can cite. `scripts/backup-sensitive` archives that directory, so machine loss is covered, but a backup is not an audit trail.

## Improving this OS
This repo improves with each interaction. After every meaningful exchange, update curated knowledge when Sam reveals new facts (clients, decisions, pricing, process), and refine outdated lines rather than appending parallel ones. Let stale things die.

But keep the mind cold. Don't fanatically follow instructions, don't over-engineer, don't pad the repo with low-value structure. When Sam says "what you recommend" or "skip", make a judgment call and act, don't escalate or re-ask.

- **Status banners:** when a file or number is superseded, put a bolded `SUPERSEDED - see <path>` line at its top (or ~~strikethrough~~ the dead number). Never leave a stale current-sounding claim un-bannered. A file that dies without a successor gets `**DEAD - <why>**` at its top in the same session any owner file rules it dead; `repo-doctor`'s `dead-artifact-ref` check (soft, both modes) then flags un-struck live-sounding references to a bannered file. On a rollup surface like `STATS.md`, only a strikethrough exempts a carried-over value; a marker sitting nearby does not.
- **Expiry:** perishable pages (web-sourced pricing, platform mechanics, eligibility research, anything true-today-not-forever) carry a `**Stale after:** YYYY-MM-DD` line near the top with a word on why. `repo-doctor` flags expired pages so staleness announces itself; re-verify or supersede, don't just bump the date.
- **Dated commitments:** anything with a deadline or tripwire gets a `**Due:** YYYY-MM-DD - <what/what happens>` line in the file that owns it. `scripts/horizon` (run at session start, and by the daily-log plan and `/weekly` modes) surfaces overdue and next-14-days items, the OS's clock. Resolve a Due line by striking it through with the outcome, never by deleting silently. Horizon sees line-start `Due:` lines **and** mid-line bold `**Due:**` tokens, and it judges a strikethrough per token rather than per line, so the rollover shape `~~**Due:** <old>~~ **Due:** <new>` reads as one live commitment and one resolved one. A Due token inside a fenced code block is treated as a paste template, never a commitment. The grammar has exactly one owner, `scripts/clock_grammar.py`, loaded by `horizon`, `money` and `repo-doctor`; do not re-copy it into a fourth consumer, because hand-copied grammars drift and one consumer starts rejecting the shape another accepts. A deadline that exists only as prose is invisible to the clock (`repo-doctor` warns on past-dated ones), and a due date in a table column is invisible too.
- **Tombstones (ripple rule):** superseding a number or decision means, in the same session: grep the dead value repo-wide, banner or strike every current-sounding hit, and add the dead string to `ai/TOMBSTONES.md`. `repo-doctor` blocks tombstoned values from reappearing un-bannered (HARD in `knowledge/`, `.claude/`, `templates/`, `skills/`; soft in `outputs/`). Ripple surfaces to grep, not just `knowledge/`: `templates/`, `skills/`, and `.claude/agents/`. Agent files hold persona and method only, never live deal state, so a status claim cannot rot there unseen. A re-price that is not rippled sits un-bannered in every satellite file that quoted it, and every one of those is a wrong number waiting to reach a client.
- **One owner per state fact:** a price, deal stage, KPI, or status lives in exactly one owning file; satellite files point to it rather than restating the value. Every copy is a future stale line.
- **Error ledger:** any mistake that reached Sam or a client gets one line in `ai/ERRORS.md`. New rules and checks must trace to a real entry there, or to a hazard named in that file's Hazards section. No speculative process.
- **Ratchet rule:** a session that fixes a class of quality problem ends by adding the floor check that makes that class un-reintroducible, where a mechanical check is possible. Cleanups without ratchets are rented, not owned. The guardrail-fixture suite (tests that the checks themselves still fire) is specified in `knowledge/ops/os-roadmap.md`.

## Hard tasks
- **Tier 1 - the skill carries the verification.** `proposal-creator` and `invoice-creator` embed mandatory verification steps: a fresh-context `fact-check` pass in both; a `price-attack` pass additionally in `proposal-creator` and for any invoiced amount that never went through a proposal (informal agreed work). Never skip them, even for "quick" work. `fact-check` and `price-attack` are subagents on Claude Code (`.claude/agents/`) and mirrored for Codex (`.codex/agents/`); on any other host, run the same pass as a fresh-context read of the artifact against its owner files, following the agent file's procedure.
- **Tier 2 - run the hard-task protocol** (`skills/hard-task/SKILL.md`, reachable as `/hard-task` in Claude Code and `$hard-task` in Codex) for high-stakes work no skill covers: legal, tax, banking, entity or relocation decisions, canonical `knowledge/` rewrites, repo reorganization, irreversible client-facing moves. Other hosts follow the same procedure by reading that `SKILL.md`.
- Everything else is judgment. When genuinely unsure, a short hard-task pass beats a confident wrong answer.

## Skills
Reusable generators live in `skills/<name>/`, one folder per skill, each with a `SKILL.md`. That folder is canonical and owns the procedure. Read the `SKILL.md` before running. New skills always go in their own `skills/<name>/` folder. **Discovery is separate from ownership:** hosts that auto-discover skills read `.agents/skills/` (Codex, invoked as `$<name>` or through `/skills`) and `.claude/skills/` (Claude Code), so `ai/AGENT_ROUTES.json` carries one `skill_adapters` row per skill and `scripts/sync-agent-adapters --write` renders a thin adapter that points back at the canonical file. Every `SKILL.md` carries `name` and `description` frontmatter, written as invocation triggers (the metadata a skills host keys discovery on), or the generator refuses to render its adapter; and `--check` fails when a `skills/<name>/SKILL.md` exists with no registry row.

**Precedence carve-out:** where this file's summary of a skill disagrees with that skill's own `SKILL.md`, the `SKILL.md` wins on execution mechanics (required fields, steps, write licences, verification order). This file wins on doctrine: precedence, voice, pricing policy, what counts as a sanctioned write. When the carve-out fires, correct the summary here in the same session, because a stale summary in the highest-precedence file is worse than no summary.

## Voice + format rules

**Cross-cutting rule (applies to X, LinkedIn, outbound, client messages):** never justify actions. No preemptive explanation, no defensive framing, no apologizing for the work. State and move on.

**No em dashes, anywhere.** Client copy, drafts, `knowledge/` files, commit messages, chat. Comma, period, or a single hyphen instead. Owner of the rule and its traces: `knowledge/voice/copy-rules.md`.
