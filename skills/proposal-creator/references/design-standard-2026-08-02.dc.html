Overview

Kestrel Wholesale runs stock in two systems that do not talk to each other: the store platform that sells it and the warehouse system that holds it. Every morning someone exports a CSV from each, lines them up in a spreadsheet, and corrects the differences by hand. The reconciliation takes about ninety minutes, and the two systems have already drifted again by the time it is finished.

This build replaces that with a scheduled sync between the two systems, a conflict log for the cases a machine should not decide alone, and an ops dashboard that shows current stock, open exceptions and the health of the sync itself.

All work is delivered by Northwind Labs, operating under Rivera Holdings LLC. The sync ships first and on its own, so the manual reconciliation stops before any dashboard work starts.

02

Scope of work

2.1 Inventory sync

Deliverable Description
Store platform connector Read and write against the store platform's inventory API, with rate limiting, retries and a resume point, so a slow or throttled hour delays the sync instead of losing writes.
Warehouse system connector The same on the warehouse side, working from its export feed and its adjustment endpoint. SKU mapping between the two systems is built from your current mapping sheet and then owned by the sync.
Scheduled sync and backfill A run every fifteen minutes, plus a one-off backfill that brings the two systems into agreement on day one. Runs are idempotent, so a re-run after a failure cannot double-count an adjustment.
Conflict handling Rules for the cases that resolve themselves, and a queue for the ones that should not. A disagreement a human has to judge is never silently overwritten; it lands in the exception queue with both values and both timestamps.
Run health and alerting Every run records what it read, wrote and skipped. A failed run, or a run that stops happening at all, raises an alert to a channel you choose. A sync that dies quietly is worse than no sync.

2.2 Ops dashboard

Deliverable Description
Stock view Current quantity per SKU across both systems, with the difference called out where one still exists. Filter by location, category and supplier.
Exception queue The conflicts the sync would not decide, with a one-click resolution that writes back to both systems and records who chose what.
Sync health panel Last successful run, current lag, failures in the past day, and the volume moved. This is how the ops lead answers "is it working" without asking anyone.
Access and export Two roles, viewer and resolver, on your existing single sign-on. Every view exports to CSV, because the finance team will want the numbers in a spreadsheet anyway.
Handover and runbook A written runbook covering deploy, credential rotation, the three failure modes worth naming, and how to pause the sync safely. Delivered with a walkthrough for whoever will own it.

Out of scope

Any work beyond the scope above is quoted separately before commencement. Specifically excluded from this engagement:

Purchase-order automation Reordering off the synced stock levels is a natural next step and a separate engagement. This build gives it clean numbers to work from.
Historical data cleanup The backfill reconciles current quantities. Correcting years of historical movement records is a data project of its own, quoted separately if wanted.
Third-system integrations The accounting package and the supplier portals are not in this build. The connector pattern is written so a third system is an addition, not a rewrite.

Definition of done

Phase Deliverables and acceptance
Phase 1 - Inventory sync Deliverables: both connectors, the backfill, the fifteen-minute schedule, conflict rules, the exception queue and run alerting. Accepted when your team picks any ten SKUs, changes stock in either system, and sees both systems agree within one sync window without anyone opening a spreadsheet, and when a deliberately failed run raises an alert in your channel.
Phase 2 - Ops dashboard Deliverables: stock view, exception queue, sync health panel, two roles on your single sign-on, CSV export, runbook and handover. Accepted when an ops lead who was not in the build resolves a real exception end to end from the dashboard alone, using only the runbook, and the resolution shows in both systems.
07

Sequencing

01 Access and mapping API credentials on both systems and a copy of the current SKU mapping sheet. Nothing else starts until both exist.
02 Sync in dry run The sync runs read-only for a week and reports what it would have changed. You approve the diff before it is allowed to write.
03 Backfill and go live Backfill runs once, then writes turn on. The manual morning reconciliation stops here, which is the point of doing the sync first.
04 Dashboard and handover Built on a sync that is already running in production, so the views show real data from the first day of the phase.
